# 首次 H100 启动：source 顺序配额冲突修复

原 run：`cfpi_pilot_20260905`，源码提交 `a564b8a`。
用户在 8 H100 上的 CUDA、MMCV、gsplat 预检均通过；13:05 UTC 在 source 阶段停止，
没有开始 baseline、分支采集或方法训练。
实际错误是 `Insufficient clean source for matched_common: 505`。

## 原因与修复边界

原实现先冻结 512 rare，再从剩余日志容量选择 common，不能回退 rare。
在两类共享每日志 4 个配额时，顺序贪心失败不等于联合问题不可行。
这属于源池选择器的实现缺陷，之前的测试未覆盖真实共享容量冲突。

只读索引统计（尚未过滤短于 20 步的场景）：排除指定日志后 rare=3466、common=3479，
两类各有 299 个日志；各自独立容量为 980/982，合并容量上界为 1116。
用旧算法仅在这些索引上可复现 512/506；实际长度过滤后即运行中的 512/505。
这些数量来自 membership，不来自实验 outcome，不能解释为选择效果。

修复首先复现原 hash 贪心选择，然后构造 family → origin-log 容量网络，
用确定性残量增广补足未满足的配额；需要时把 rare 名额移到有剩余容量的日志。
日志内选择仍取原 scene hash 排名前缀。若贪心本来成功，结果不变。
若联合问题仍不可行则继续失败，不取消 512/512、每日志 4 个或 15 个排除日志。
不读取候选奖励、分支返回、validation/test 数据，也不重新定义 rare/common。

源池审计新增 `source_selection`，记录有效场景数、容量、原贪心配额、增广次数、
最终配额和移出的原贪心场景数；实际结果以 r2 的 `source/source_audit.json` 为准。
测试新增共享容量冲突反例、729 种容量结构的穷举可行性对照、
source 入口的长度/排除过滤、物化、恢复及上游变动拒绝。
同时去掉 first_phase 中重复准备一次 source 的调用，避免无意义重复扫描。

## 重启与预算

必须使用 `cfpi_pilot_20260905_r2`，因为源码/协议哈希改变。
保留原 run 的日志和 contract，不删锁、不篡改旧合同，不将旧结果冒充新运行。
原账本使用 0.1649841367 GPUh；r2 上限保守设为 143.8 GPUh，
两者合计不超过原 144 GPUh 上限。启动与恢复都必须保留这个参数。

在助手完成 CPU source 物化后，可从 H100 实例直接运行 RUNBOOK 的 r2 first_phase；
它会重新预检并验证已有 source 的字节哈希，然后才启动 baseline A/B。
旧硬件阻塞说明是历史记录，不适用于用户已通过预检的 H100 实例。
